Caching strategies

The fetch event in the service worker decides where every answer comes from. There are a few common ways to do it, and an app can use different ones for different files.

Cache first

Look in the cache, and only go to the network if the file is not there. This is the fastest and works fully offline. All apps on this site use it, since their files only change when a new version is built.

self.addEventListener("fetch", function (event) {
    event.respondWith(
        caches.match(event.request).then(function (cached) {
            return cached || fetch(event.request);
        })
    );
});

The catch: the user does not see a change until the cache is replaced. See Updates for how a new version reaches them.

Network first

Ask the network, and use the cache only when that fails. Good for things that change often, like a news page, but it is slow on a bad connection since it waits for the network first.

self.addEventListener("fetch", function (event) {
    event.respondWith(
        fetch(event.request)
            .then(function (response) {
                // Save a copy for next time we are offline.
                const copy = response.clone();
                caches.open(CACHE).then(function (cache) { cache.put(event.request, copy); });
                return response;
            })
            .catch(function () {
                return caches.match(event.request);
            })
    );
});

An answer can only be read once, so response.clone() makes a copy for the cache and the original goes to the page.

Stale while revalidate

Answer from the cache at once, and at the same time fetch a fresh copy for next time. Fast like cache first, and the app is never more than one visit behind.

self.addEventListener("fetch", function (event) {
    event.respondWith(
        caches.open(CACHE).then(function (cache) {
            return cache.match(event.request).then(function (cached) {
                const fresh = fetch(event.request).then(function (response) {
                    cache.put(event.request, response.clone());
                    return response;
                });
                return cached || fresh;
            });
        })
    );
});

Network only

Some requests must never be cached, like an API that gives a new answer every time. Just leave them alone: if the worker does not call event.respondWith(), the browser handles the request as usual.

self.addEventListener("fetch", function (event) {
    const url = new URL(event.request.url);
    if (url.hostname === "api.ipify.org") return;   // Always ask the network
    // ... cache first for everything else
});

Which one to use

  • The app's own HTML, CSS, JavaScript and images: cache first, with a new cache name for every version.
  • Content that changes, like a list loaded from a server: network first or stale while revalidate.
  • Live data, logins and anything that posts: network only.
